#For developers

#Where to start

  • CLAUDE.md in the repository root: how to build, test and release, the git workflow, and the invariants that bite.
  • docs/ARCHITECTURE.md: the flow from the collector to the views and a map of every source file.
  • docs/adr/: the decisions behind the shape (one binary, patterns as decisions, no blanket trust of interpreters, compressed history, signing, fewer patterns, one module with one-concept files).

#Build & run

./scripts/build-app.sh
open dist/Hostwatch.app      # prompts for an admin password to start the collector

#Test

./scripts/test.sh

This runs every automated test, in about 30 s. There are three suites.

Only part of it, while working:

./scripts/test.sh --changed                       # the suites that mention types declared in files changed since main
./scripts/test.sh --only 'FewerPatterns|RuleText' # suites or tests matching a regex (swift test --filter)

--changed finds the types the changed source files declare and runs every suite whose file mentions one of them (a changed test file runs as itself). It is a shortcut for the edit loop; the merge gate still runs everything.

Swift (tests/swift, Swift Testing, swift test) covers:

  • pattern grouping and risk rules
  • Stories: attack chains must fire as Dangerous, and everyday dev work and known false positives must stay quiet
  • code signing on real unsigned / ad-hoc / quarantined / replaced binaries made in a temp folder
  • new-domain baseline and badges
  • beaconing maths and rules, and raw-IP rules
  • Homebrew tools not trusted by signature, on a real Homebrew binary when one is installed

Tests use in-memory engines and a scratch signing database, so they never touch your data.

Collector (tests/swift/AgentTests.swift) covers:

  • DNS answers, pktap SYN and nettop parsing, with real lines captured on a Mac
  • destination inference
  • secret masking and exclusions
  • JSON output identical to the former Python collector
  • busiest processes and Hostwatch's own activity
  • the socket's permissions and peer checks
  • that helpers get a pipe as stdin and no inherited files

Performance budget (tests/swift/PerformanceBudgetTests.swift) runs the same realistic workloads every time and measures CPU time, bytes written to disk and memory (kept and peak) against tests/perf-baseline.json. Each test runs alone, in its own process, after the rest, so other tests don't count.

  • The workloads: 40,000 events through the app's pipeline with a 15,000-pattern store saved on schedule; 100,000 events through the compressed history writer; 120,000 eslogger events through the collector's reader; a Time Travel page and a full search.
  • The budget: a change fails the tests when it writes more than +20%, keeps or peaks more than +30% memory, or uses more than twice the CPU (plus small allowances; CPU time depends on which cores macOS picks).
  • What it catches: the regressions found so far, such as the pattern store rewriting itself (87 MB written instead of 4 MB), history written uncompressed (24 MB instead of 2 MB), and the collector's reader keeping what it read.
  • A new baseline: after a change meant to cost more (or less), record one on purpose and commit it: HOSTWATCH_PERF_RECORD=1 ./scripts/test.sh. Each workload runs 3 times and the highest figures are kept. Numbers are from the debug build on the Mac they were recorded on; on a much faster or slower Mac, record a baseline there.

Local MRs are gated. scripts/hooks/pre-merge-commit runs the tests on the merged result and refuses the merge commit if anything fails.

  • Enable it: git config core.hooksPath scripts/hooks. It is already set in this repo. Run it again after a fresh clone.
  • Emergency bypass: git merge --no-verify.

Manual check with the collector running:

/usr/bin/id                          # ▶ process
curl -sI https://example.com >/dev/null   # ▶ process + 🌐 connection
cat ~/.zshrc >/dev/null              # 📄 file

#Demo mode (screenshots)

Demo mode fills the app with made-up activity, for screenshots and the website. It exists only in the demo build. The normal build, and every release, has no demo code at all.

Build it: DEMO=1 ./scripts/build-app.sh makes dist/Hostwatch Demo.app. It uses the Swift flag -DDEMO, its own bundle id local.hostwatch.demo and its own build folder .build-demo.

Run it: "Hostwatch Demo.app/Contents/MacOS/Hostwatch" --demo <folder> [hud|events|live|running|patterns|stories|network|firewall|watch]

  • What it shows: the activity of a made-up user (/Users/alex). That is everyday work plus a fake download that removes its quarantine, reads cookies and the keychain, adds a launch agent and calls home.
  • Scene: it opens the scene you asked for.
  • live: keeps adding events about once a second. This is for the website's background video, recorded with screencapture -v and encoded with ffmpeg.
  • Isolation: everything it keeps goes to <folder>. It never connects to the collector and starts nothing as root.
  • Tests: ./scripts/test.sh also runs the demo tests against the demo build.

#Prototype notes

Apple documents eslogger as a tool for exploring and prototyping, not an application API. Its JSON may change without notice.

For a distributable tool, replace the collector with:

  • a native Endpoint Security system extension (com.apple.developer.endpoint-security.client entitlement)
  • a Network Extension for connections

#Production architecture

For production, implement a signed Endpoint Security system extension. Use XPC or a protected local IPC channel to communicate with this HUD.

The system extension should:

  • subscribe only to the event types required
  • process callbacks quickly
  • avoid blocking ES callbacks on UI or disk I/O

Apple's ES entitlement must be approved for the developer team. Do not disable SIP as a routine installation workaround.
