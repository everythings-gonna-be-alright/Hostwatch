How Hostwatch works. Every feature, setting and rule.

Built from the same reference that lives in the repository, so it's always current. New here? Start with the install steps, then read on in order.

Every feature, setting and rule of Hostwatch, in the order you'll meet them. For a short overview, see the README; the same text is on the website at https://everythings-gonna-be-alright.github.io/Hostwatch/docs/.

#Getting started

#Requirements

  • macOS 26 or later (Liquid Glass UI; eslogger is included)
  • Xcode 26 Command Line Tools (Swift 6.2+, macOS 26 SDK)
  • Full Disk Access for Hostwatch.app (or Terminal, when using run-agent.sh)
  • Administrator password for the collector

Install tools if needed:

xcode-select --install

#Install

  1. Download Hostwatch-<version>-macOS-universal.zip from Releases and check it: shasum -a 256 Hostwatch-*.zip must match the .sha256 file next to it.
  2. Unzip and move Hostwatch.app to /Applications (somewhere only you can write to: the collector runs from it as root).
  3. It isn't notarized: open it once, then allow it in System Settings ▸ Privacy & Security ▸ Open Anyway.
  4. A setup window asks for Full Disk Access (Open Settings…, then Quit & Reopen). Start Without Access watches the network only; Later / Not Now close the guide; Start Watching continues once access is on.
  5. Enter your administrator password once: the collector starts and the first-hour baseline begins.

#Built-in collector

The collector is built into the app: there is no separate script. At launch (toggle Settings ▸ General ▸ Start collector when Hostwatch opens), the app checks for an existing collector socket (/var/run/hostwatch/collector.sock). If none is running, it asks for an administrator password and starts it as root as a temporary launchd job (system/local.hostwatch.collector, gone after reboot). The job runs Hostwatch --collector-launcher, which spawns the agent. macOS then treats Hostwatch.app as the responsible process for eslogger, so Full Disk Access must be granted to Hostwatch.app, with output going to ~/Library/Logs/Hostwatch/agent.log (Help ▸ Collector Log).

  • Stop Collector sends a shutdown command carrying a random token. The token is written with mode 0600 to ~/Library/Application Support/Hostwatch/collector.token and passed to the agent.
  • The agent also exits within about 2 s if the app that launched it dies (--owner-pid).
  • eslogger needs Full Disk Access. If the log shows ERR_NOT_PERMITTED, use Open Full Disk Access Settings and enable Hostwatch, then start the collector again. The app checks for this before asking for your password and shows a guide if access is missing. Builds are ad-hoc signed by default, so every rebuild needs the grant redone: remove the old Hostwatch entry with − and add it again. To avoid this, build with a stable identity: CODESIGN_IDENTITY="Apple Development: you@example.com (TEAMID)" ./scripts/build-app.sh.
  • ./scripts/run-agent.sh runs the collector by hand from Terminal (sudo Hostwatch --collector). The app detects it and does not start a second one.

#Baseline: the first hour

On the first launch Hostwatch learns in three waves, at 5, 15 and 60 minutes. Each wave sorts the New patterns seen so far (BaselinePolicy):

  • Trusted (Safe, source "baseline"): normal risk, the acting program (and for a launch the launched one) signed by Apple or by the developer of an installed app, valid signature, not quarantined, not in Downloads / temp / Shared / a volume, and not touching a sensitive place (login items, credentials, mail, messages). macOS system services (daemons and agents on the sealed system volume, not command-line tools like cat, sqlite3 or a shell) may touch sensitive places: indexing, sync and malware scanning is their job.
  • On-device model (never Claude): signed, but the developer isn't trusted yet. Its verdicts are suggestions in Needs You; it never suggests Safe for high risk.
  • Needs You (stays New): high risk, unsigned or ad-hoc, quarantined, Downloads or temp, sensitive places, or the program is gone. Malware already on the Mac lands here, so the baseline can't be poisoned.
  • Hostwatch's own activity, and interpreters and shells (macOS's own included), are never trusted or listed (they stay New).

Baseline rules (Rules tab) are narrow: one per app and its signer (Slack · Slack Technologies; the app's helpers included, and the signer must match), and one macOS system rule. A rule keeps trusting that app's future normal-risk patterns (checked every 30 s, always through the same policy). After learning, a new app isn't added by itself: Update Baseline (local, code signatures only, no AI) sorts New patterns again and adds rules for trusted apps among them.

  • Pause a rule: its patterns go back to New and it stops applying (kept, so Update Baseline won't recreate it). Delete does the same and removes it; ⋯ ▸ Remove All Baseline Rules removes every baseline rule.
  • Decided isn't forever. A Safe pattern, whoever decided it (you included), is reopened, back to New and listed first in Needs You as Reopened: …, when:
    • one of its steps is part of a story that fires (part of a story: Slack → sh → curl);
    • its program contacts known malware infrastructure or is a known malware file (every Safe pattern of that program);
    • it becomes high-risk: the binary was swapped or modified, is quarantined or runs from a download/temp folder.

A reopened pattern is never decided again by a baseline rule, a learned rule, Accept AI suggestions without asking or Classify with AI; your own decision (Mark, Trust, Accept) closes it. Decided By shows Reopened. New kinds of behaviour from a trusted app reach you through its rule's profile (above).

  • Low weight: your markings and learned rules win over baseline rules, and stories ignore baseline trust (they count only your decisions and learned rules), so a chain still alerts.
  • Needs You has one row per app with all its reasons (for example signed by Zoom (trusted developer, no rule yet) for an app installed after learning):
    • Trust marks its patterns Safe (your decision). For a signed app it also adds a baseline rule marked Trusted by you, which also covers that app's own sensitive places (never high-risk, unsigned or downloaded). Unsigned or ad-hoc programs are trusted pattern by pattern, with no rule.
    • Interpreters and shells (python, node, ruby, bash, osascript…) aren't listed: they run any script they're given, so trusting them would trust a virus's script too. Their patterns stay New, visible in Patterns, and stories keep watching them.
    • Dismiss hides the row; its patterns stay New and aren't listed again.
    • Click N patterns › to list them in the row. ⋯ ▸ Mark Suspicious, or Show in Patterns, which opens exactly those patterns (a removable chip replaces the Show filter).
  • Existing installs don't start learning by themselves: Update Baseline (Rules tab or Settings ▸ Detection).
  • Fewer decisions for you:
    • macOS itself is always trusted: Apple tools on the sealed system volume (also when a trusted app starts them: Cursor running /bin/rm) fall under the one macOS system rule, made by itself, from the first minute.
    • New apps from developers you trust get a rule by themselves (Settings ▸ Detection ▸ Trust new apps from developers you trust, on), marked Automatic. A rule you delete isn't made again by itself (Update Baseline still can).
    • A rule trusts only what its app normally does: in its first week it learns the app's kinds of behaviour (launches node, connects to the web, reads ~/Documents, writes its own data…); after that a pattern of a new kind isn't trusted and comes to Needs You as new for Slack: writes ~/Movies. Rules from before this keep what they already trusted as their profile. macOS's own rule doesn't learn a profile.
    • Needs You lists only what's active: a pattern not seen for 7 days leaves it (it stays New in Patterns and comes back if it happens again). Homebrew tools share one row.
    • Rules ▸ Rules shows Trusted automatically in the last 24 hours: N new patterns (Docker 12, …) with Show.
  • Baselines from the first version (one rule per developer) are undone once and sorted again.

#After a restart

The event list starts with the newest recorded events from history (up to its 5,000-event limit), so it isn't empty; the footer shows how many came from before the restart. They are display only (detection already saw them) and sort below every new event. Time Travel shows the rest.

#Everyday use

#Controls at a glance

Each kind of control has one home.

  • Menu bar icon (the app icon's list mark, tinted like other menu bar icons): a glance and quick actions.
    • Status line: Live, Paused, Starting… or Collector off; open stories; high-risk patterns.
    • Extra lines when they apply: N processes held — Review…, N known-bad matches this week…, A macOS update fixes N exploited flaws… (or N exploited macOS flaws since your last update…), Claude Code guard was removed — Restore, Claude Code: N actions blocked today…, Learning this Mac's normal behaviour (wave N of 3), <version> Available….
    • Start Collector… when it's off, Open Hostwatch (⌘O), Stories, Patterns and Network with badges (Network shows waiting firewall questions, or else new domains), Pause Live Stream, Show HUD (⌃⌥⌘H, works from any app), Hold Suspicious Processes, Settings… (⌘,) and Quit (⌘Q).
  • App menus (while a Hostwatch window is open):
    • Edit: Undo, Redo, Cut, Copy, Paste, Select All, Find (⌘F).
    • View: Events ⌘1 · Patterns ⌘2 · Rules ⌘3 · Stories ⌘4 · Network ⌘5, Running Now (⌥⌘R), Time Travel (⌥⌘T), Earlier (⌘[) and Later (⌘]) during Time Travel, the Show filter, event-kind toggles, Show HUD, Enter Full Screen (⌃⌘F; Esc leaves).
    • Activity: Pause Live Stream, Clear Events (⌘K), Ask AI About Selection (⌘↩), Watch Selected Process Closely… (⌥⌘W), Mark Safe / Suspicious / Dangerous / Unclassified, Exclude Selection…, Start/Stop Collector.
    • Window: Activity Window (⌘0), Held Processes.
    • Help: Hostwatch Help (these docs), Use with Claude Code…, Collector Log, Full Disk Access Settings.
  • Right-click a row (events, patterns, domains, and the HUD while click-through is off):
    • Ask AI: Is This Dangerous?… and Watch <name> Closely…;
    • mark its pattern, or Mark All … From This Process (with Clear Rule);
    • Exclude ▸ Hide process, Hide spawns of, Hide host, Hide domain \.x*, or Edit Exclusions…;
    • Copy Detail, Copy Process Path, Reveal in Finder.
  • Events toolbar: the tab bar, event-kind counters (click to hide a kind), Time Travel, Pause, Clear, HUD, Settings and search.

#HUD

A compact macOS activity overlay (optionally click-through). One line per event:

IconKindShows

🌐 greennew connectionname, TCP/UDP remote:port, time

Kind toggles only hide rows: collecting, patterns, stories and history always get every kind. Turning Click-through off (it's off by default) lets you move and resize the HUD with the mouse: drag its header bar to move it and the ◣ grip in its bottom-left corner to resize. Width changes smoothly; height snaps to whole rows; the top-right corner stays put. Position and size are remembered. Quitting also stops the collector the app started.

You can also drag the HUD's left edge (width only) or bottom edge (height only). It starts at 24 rows × 360 pt. A row of CPU, memory, network and disk sits at the top unless you turn it off (Settings ▸ HUD).

#Window tabs

Show (Events and Patterns, also View ▸ Show) is a scope bar: All · New · Important. New: not decided yet; Important: Suspicious and Dangerous plus new high-risk (new domains, beacons, raw IPs and known-bad matches count as both). Each choice shows how many rows it would list in that tab: events on Events (with the kind toggles, search and Only These as they are), patterns on Patterns. It applies to the HUD, Events and Patterns.

Events ⌘1 · Patterns ⌘2 · Rules ⌘3 · Stories ⌘4 · Network ⌘5 (domains and the firewall), each with its icon and its count as a badge (icons only when the window is narrow); the event-kind counters appear on Events only. When exploited macOS flaws aren't fixed yet, a slim banner at the top says so (Details, Software Update, ✕ until another flaw is listed).

#Running Now

The Events tab's switch (Events · Running Now, or View ▸ Running Now, ⌥⌘R) swaps the event list for every process running at this moment, refreshed every 3 s while the window is on screen:

  • Columns: process (with its app's icon; ✦ when Hostwatch saw it start), PID, user (root in orange), % CPU (since the previous refresh; orange from 50%), CPU time, memory (physical footprint, as Activity Monitor's Memory), threads, running for, parent. Sort by any column; the search field matches name, path, command line, user or PID. The footer totals CPU and memory.
  • Details (select a row): path, parent, user, started, running for, CPU now, CPU time, average CPU share since it started, memory, threads, the full command line (secrets masked), and the pattern status of its launch when Hostwatch recorded it.
  • Show Spawn in Timeline (double-click, or the button): opens Time Travel at the moment the process started, with its launch selected (the search, Only These and a Show filter that would hide it are cleared). A process that started before the recording began can't be shown there.
  • Also: Watch Closely…, Ask AI… (when its launch was recorded this session), Reveal in Finder, Copy Command Line, Copy Path, Copy PID.
  • How: the app asks the collector, which (as root) reads every process with libproc (proc_pid_rusage, the task info and KERN_PROCARGS2 for command lines) and answers with one list. CPU % is the difference between two lists. Nothing is asked while the list is closed or the window is hidden, except the once-a-minute list recorded for Time Travel (below).
  • In Time Travel: Running Now shows what was running at the playhead: the list recorded at or just before it, rebuilt between that list and the next: processes appear at the moment they started, CPU time and memory move between the two lists, CPU % is the rate across them, and "running for" counts to the playhead. It follows the playhead as you drag or play. Hostwatch records the list once a minute while the collector runs and history is on (Settings ▸ History), into History/processes-YYYYMMDD.jsonl: every process each 30 minutes, only what changed in between (a few tens of MB a day, compressed when the day is over, counted in the history size limit and removed together with the activity history). Moments from before this recording started, or more than 3 minutes after the last list (Hostwatch closed), say so.

#Heavy processes

Processes Hostwatch saw start that are still running and using a lot stand out in Events (apps that were already running when it started aren't followed, or Xcode and browsers would be flagged all day):

  • Heavy means sustained: CPU averaged over 30 s (at least 25 s of samples) at or above the limit (default 50% of one core), or a memory footprint at or above the limit (default 1 GB). Settings ▸ Detection ▸ Heavy processes sets both, or turns it off.
  • The launch row gets a live badge (🔥 380% CPU · 2.1 GB · 12 min, or a memory chip when memory is the reason) and a flame in Status; the HUD shows 🔥 380%. When the process exits, the badge turns grey (ended 1 min ago · peak 240% · 900 MB) for 10 minutes.
  • A banner above the list names the heavy ones: app icon, name (with an Untrusted tag when it is), the program that started it, a CPU gauge (400% fills it), memory and running time; ✦ asks AI and ⋯ has Show in Finder and Copy Path. Only These filters Events to them; the chevron collapses it to one line (the busiest names), so it never hides that something is there.
  • Time Travel uses the same design: the heavy list is recorded with each 5-second metrics sample (usually 0–3 entries), so at the playhead the banner reads Running heavy at 14:32:05 and the launch rows carry the same badges as they did live (the running time is computed for that moment).
  • Detection: a heavy process that is unsigned, ad-hoc, quarantined or from a download/temp folder adds the story stage Heavy untrusted process (3 points, strong): the cryptominer pattern.
  • How: every 5 s the collector's existing sampler (libproc proc_pid_rusage, already used for the busiest processes) also sends every process above a floor (≥ 5% CPU or ≥ 300 MB, at most 50) with its start time; launch events carry the start time too (pstart), so a reused pid is never mistaken for the process that started. Exits are checked with kill(pid, 0). Launches restored from history after a restart are followed too. Nothing new is recorded; only numbers.

#Resource use (CPU, memory, network, disk)

Every 5 seconds Hostwatch records system-wide resource use. The Events tab's footer shows it live with 5-minute sparklines: CPU (share of all cores), Mem (apps + wired + compressed, the same as Activity Monitor's "Memory Used"; the line turns orange or red with macOS memory pressure), network download ↓ / upload ↑ (Wi-Fi, Ethernet, cellular; VPN tunnels and loopback aren't double-counted) and disk read/write. The list button shows the busiest processes at that moment (CPU % of one core, memory footprint, disk throughput).

  • Sources: CPU, memory and network come from the kernel's counters (no special rights). The busiest processes and disk throughput come from the collector: as root it can see every user's processes (proc_pid_rusage), which the app can't (about a third of processes, all of them system ones). It sends them every 5 s only to the live window, never into the event history.
  • Recording: one line per sample in History/metrics-YYYYMMDD.jsonl (a few MB per day); past days are gzip-compressed, and days older than the oldest activity history are deleted with it. Clear History removes them too. Resource use is recorded while Hostwatch is open.
  • Time Travel: the timeline shows CPU (blue) and memory (green) lines under the activity bars, on the same time axis. The footer strip shows the slice around the playhead, and the banner shows the values and the busiest process at the playhead. Times before this feature existed simply have no line.
  • Hostwatch --metrics-probe prints three readings, for comparing with Activity Monitor or top.

#Time Travel

Time Travel in the activity window's toolbar (or View ▸ Time Travel, ⌥⌘T) switches the Events tab from the live stream to recorded history. Live collection carries on in the background.

  • Timeline (floating, at the bottom): bars show how busy the Mac was across the whole recording (square-root scale, so one burst doesn't flatten the rest; gaps are when nothing was recorded). Red and orange dots mark stories, purple dots new domains. Hover for the time, drag to move; clicking near a dot lands on it.
  • The slice: the list shows the window ending at the playhead (1 min, 5 min, 15 min or 1 hour), newest first, with the same Show filter, kind toggles, exclusions and search as live. A very busy slice shows its newest ~20,000 events and says so.
  • Search all history: type in the toolbar search field (two characters or more) and the list shows matches from everything recorded, not only the slice: newest first, with the day in the Time column, and tick marks on the timeline where they happened. It matches what the live search matches (name, path, detail, host, or the exact PID). The search runs in the background and the list fills as it goes (≈5 s for 20 GB of history). It stops at the newest 1,000 matches and says how far back it got; a more specific search reaches older ones. Double-click a match (or Show in Timeline) to open its moment, with it selected. The scope bar switches between All History and This Window (only the shown slice).
  • Moving: ⌘[ and ⌘] (or ◀︎ ▶︎) step one window; ▶︎ plays forward at 1× (real time), 10×, 60× or 600×; the date picker jumps anywhere. Return to Live (Esc) goes back.
  • From a story: Show in Timeline opens the slice around it.
  • How it reads history: in the plain (current) file lines are in time order, so the offset of any moment is a binary search away; compressed files are found through their block index, and bar heights come from byte counts (per-minute counts for compressed files). Nothing is loaded except the slice you look at (the overview takes milliseconds; a busy slice of ~20,000 events ≈0.3 s). A search reads blocks newest first and parses only lines whose bytes contain the search text. Hostwatch --time-travel-probe [dir] prints these timings, searches included.

The banner has the window (1 min, 5 min, 15 min, 1 hour), the playback speed (1×, 10×, 60×, 600×) and a date picker.

#Features

#Patterns: learn normal, surface the strange

Every event gets a signature, a normalized fingerprint of who did what. Events with the same signature are grouped into one pattern:

KindSignatureExample
processparent program → executableMicrosoft Excel → /usr/bin/osascript
connectionprocess → proto, host bucket, portSlack → TCP internet:443, curl → TCP 45.33.*.*:8081
fileprocess → mode, folder or filerg → r ~/Documents/work/src/*, rg → r ~/todo.txt, agent → r ~/.ssh/* [SSH keys]

Normalization: home → ~, $TMPDIR, UUIDs, hex IDs and version numbers → placeholders (also in executable names that are only a version, e.g. claude/versions/#.#.#).

The general rule: no pattern covers a whole area (SignatureBuilder.specificPath, for every program). A wildcard needs at least 2 folders below home (~/Documents/work/*) or 3 elsewhere (/Users/Shared/tools/*); a file in a shallower folder is its own pattern (r ~/todo.txt, r ~/Documents/a.pdf, r /tmp/x.log, r /usr/bin/ls). Patterns name the file's folder; for apps, trees deeper than 4 folders below home (5 elsewhere) end in /** there (~/Projects/app/node_modules/a/**), while interpreters and shells always get the exact folder. So r *, r ~/*, r ~/Documents/**, r /*, r /tmp/* or r /Users/** never exist, can't be a learned Safe rule, and "Mark All … From This Process ▸ Safe" is gone (Suspicious or Dangerous for a whole program still work). Undecided or automatic wide patterns from earlier versions are dropped at launch; ones you decided stay. On a real day of history: 1,219 → 2,803 patterns, mostly routine (auto Safe); patterns to decide 150 → 227. Labelled places stay as before:

  • sensitive places, for any access: SSH/GPG keys, cloud and registry credentials, keychains, TCC, cookies, Safari/Mail/Messages data, browser credential stores, local accounts, sudoers. These are tagged [label].
  • autostart locations, for writes only: LaunchAgents/Daemons, cron/at/periodic, login items and shell rc files. These are tagged [persistence].
  • an app's own data folder: ~/Library/Application Support/<App> or ~/.<app>, when the name matches the actor. These are tagged [own data].

Built-in safe patterns. macOS's own behaviour, the same on every Mac, is decided as routine out of the box (BuiltInSafe): any program reading ~/.CFUserTextEncoding (CoreFoundation's text-encoding preference); /usr/sbin/networksetup running /bin/sh -c ‹/bin/cp …/SystemConfiguration/preferences.plist …› (its settings backup); sh/bash /usr/libexec/tmp_cleaner (Apple's temp clean-up script); and SystemUIServer running screencapture …com.apple.screenshot.launcher… (a screenshot you took). Only exact patterns; when a parent is named it must be that program on the sealed, read-only system volume, so a copy elsewhere or the same command from another program doesn't count. Signing still applies (a swapped binary is high-risk) and stories ignore automatic decisions. Existing New patterns that match are decided at the next launch. Your own developer activity (scripts, hooks, kubectl, codesign…) isn't universal, so it's not built in: mark it, combine it or let rules learn it.

Combining patterns. Select two or more patterns of one kind in Patterns, then right-click (or Mark Selected) ▸ Combine… into One Pattern. A sheet proposes the shared pattern: their common shape, token by token, with * where they differ (r ~/Documents/work/alpha/* + …/beta/* → r ~/Documents/work/*/*), editable for the program and the pattern. It must cover every chosen pattern and stay specific (the general rule above; bare wildcards refused). Every existing pattern it covers is merged too: counts add up, first and last seen span them, the most serious status wins (Dangerous, Suspicious; New when Safe and New are mixed). From then on, activity whose own pattern it matches joins it instead of creating a new one, and rows already on screen follow it. Separate Combined Pattern undoes it (new activity makes its own patterns again).

Tidying (routine noise only). 30 seconds after launch and then daily, Hostwatch removes routine Safe patterns (decided automatically as ordinary: system reads, caches, scratch writes) not seen for 30 days (they come back if they happen again), and folds routine Safe patterns of one program that differ only in random parts (a token with digits and letters such as cache-aB#dE#, <hex>, <uuid>, or a long mixed-case code) into one combined pattern, marked automatic. A fold needs at least 3 patterns, must pass the not-too-wide rule and may cover nothing but routine Safe patterns. Nothing New, reopened or decided by you, a rule, the baseline or an AI is touched; and if activity that joins a fold later isn't routine, the fold goes back to New. On a real store: 16,490 → 15,963 on the first run (62 folded into 14), pruning grows as patterns age. The Patterns footer shows the last result.

Group by Process (on by default) shows one row per program (by name) with its patterns under it: the most serious status and risk among them, how many are New, the kinds of activity, the total count and first/last seen. A program with one pattern stays a plain row. Marking, deleting or asking about a program's row acts on all its listed patterns; right-click it for Show Only that program. Columns: Status, Kind, Process, Pattern, Decided By, Signer, Reason, Count, First Seen, Last Seen.

One-offs. A pattern seen only once, not high risk, not Suspicious or Dangerous and not decided by you or your rules (a command typed once, a one-time connection) is recorded like any other: detection works the first time. The Patterns tab hides it unless Seen Once is on (search and scoped lists find it anyway). Tidying removes it when it hasn't happened again for 7 days, if it's undecided or Safe only automatically (routine), unless an open story uses it; ones an AI or the baseline decided stay. If it happens later, it's simply new again.

Connections: public IPs on web ports (80/443/53/853/123) become internet. Other ports keep the /16. Loopback, LAN, link-local, CGNAT and multicast are named. Ports ≥ 49152 become ephemeral.

Risk. Each new pattern gets a local risk level, computed only from what is in the pattern:

  • routine: auto-marked Safe (source auto), never sent to Claude and never highlighted as NEW. This covers reads of system, app, cache and container files; scratch writes (temp, caches, containers, prefs); anything done by binaries on the sealed system volume (except LOLBins like curl and osascript); launchd/xpcproxy starting system services (one pattern); loopback traffic; and an app touching its own data.
  • high, shown with a 🔥: access to a sensitive place by a non-owner, persistence writes, executables running from temp/Downloads//Users/Shared/volumes, GUI apps spawning shells/interpreters/LOLBins, and LOLBins talking to public IPs on unusual ports.
  • normal: everything else.

Code signing refines that, looking only at the binary the pattern names (what runs, or what acts). Each binary is inspected once per version (Security framework: signed or not, ad-hoc, Apple, Team ID, organisation, CDHash, quarantine flag). Its signature is fully validated in the background, and checked again when the file changes:

  • Unsigned or ad-hoc code that is quarantined or runs from a download/temp folder → high. Unsigned code elsewhere (Homebrew, your builds, bundled runtimes) is left to the path rules.
  • Apple or a trusted developer doing non-sensitive things → routine. Sensitive places, autostart writes and spawning shells/LOLBins keep their rules.
  • Signature no longer matches the binary (modified) → high.
  • Binary replaced: a known path whose signer changes in a way an update wouldn't explain (signed → unsigned/ad-hoc, Apple → non-Apple, different Team ID) → high, plus a Stories stage.
  • Trusted developers start as the Team IDs of the signed, non-quarantined apps already in /Applications (your baseline). New vendors stay untrusted until you right-click a pattern → Trust Developer “…”, or remove one with Stop Trusting. Patterns are re-scored right away. Facts are saved in ~/Library/Application Support/Hostwatch/signing.json.

#Beacons and raw-IP connections

Two more per-connection signals (like new domains, not part of pattern keys):

  • Beaconing: one program contacting one destination (domain, or IP without a name) at a steady interval: at least 6 contacts, average gap 10 s–1 h, jitter ≤ 25%. Many apps do this legitimately (Slack's heartbeat every ~2 min, telemetry), so it only counts when the program is untrusted or a system tool (curl, python, …), or the destination is a raw IP or a new domain. Then the connection carries BEACON ~60s and a strong Beaconing stage goes to Stories.
  • Raw-IP connection: a public IP on an unusual port (not 80/443/53/853/123) with no DNS answer before it, from an untrusted program or system tool → RAW IP badge and a Raw-IP connection stage in Stories.
  • Both pass Only Important and Only New. On ~2 hours of real history: 0 beacons and 0 raw-IP alerts; the one periodic flow (Slack → slack.com every ~125 s) was correctly ignored.

Homebrew ad-hoc-signs what it builds, so signing can't vouch for git, kubectl, fish…: they're judged by the path rules like your own builds, and you decide their patterns. End Now for domain learning is in Settings ▸ Detection.

#Firewall

Settings ▸ Firewall: Off, Watch, Ask or Strict. The connections themselves are in the Network tab (⌘5), next to the domains (see below). Watch judges every connection Hostwatch sees (TCP and UDP) with the firewall's rules (FirewallPolicy), first match wins: local network (loopback, LAN, link-local, multicast) and Hostwatch itself pass; a known malware address blocks (even if Safe); a pattern marked Suspicious or Dangerous blocks; Safe passes; then by risk: high-risk blocks, routine (macOS, trusted developers) passes; a sealed macOS binary that isn't a shell or tool passes; anything else new is asked about. What wouldn't simply pass is listed (Network tab, last 7 days, at most 500, in firewall-watch.json), judged again with each pattern's current status; Allow / Block mark the pattern Safe / Suspicious. Watch blocks nothing.

Ask and Strict turn on the relay in the collector (AgentFirewall, FirewallRelay, PFRedirect). pf rules in the anchor com.apple/hostwatch (inside Apple's, which /etc/pf.conf loads) send every new outgoing TCP and UDP connection of non-root users (not _mdnsresponder, not loopback, LAN, link-local, multicast, CGNAT) over lo0 to the relay on port 46110 (loopback only), IPv4 and IPv6, every interface. Connections already open aren't touched. For each one the relay finds the original destination (DIOCNATLOOK, else pf's state table), the program (the process holding the client's port, SocketOwner) and, for TLS, the server name (peeked, nothing decrypted), then asks the app (fw_ask, one question per program, protocol, destination and port however many connections wait). The app answers with the rules: allowed → pass (remembered 5 min), blocked → refused (1 min); something new is refused in Strict, and in Ask waits, with no time limit, while its own window asks Allow / Block (one window per question, in the middle of the screen; your answer marks the pattern Safe or Suspicious and answers its other waiting connections). Ask Claude in a question window gathers the same evidence as Ask AI (signature, location, parent, quarantine, the connection) with the firewall's question first, and shows Claude's short advice in the window: Allow or Block and why, then the program, the destination and the risks, with a verdict and 0–100 risk badge (it never answers for you). Leaving Ask decides what still waits by the new mode (Off or Watch: pass; Strict: refused). Without the app, Strict refuses and Ask passes. TCP is relayed with BSD sockets (half-closes passed on exactly), UDP as flows (ended after 60 s quiet, 10 s for DNS); relayed flows the other sources missed (UDP mostly) become net events. Fail-safes: the redirect is removed when the mode leaves Ask/Strict, when the collector stops, by a watchdog in its own session when the collector's process is gone, at the next collector start (stale rules), at reboot (anchors live in memory), and when the web check through the relay (curl as nobody, every 30 s) fails twice, which also switches the app back to Watch. Not covered: programs running as root, macOS's DNS lookups, the local network; Hostwatch itself always passes. Test tools (as root): --firewall-probe (two test destinations) and --firewall-relay-test [s] (your real traffic through the relay, blocking nothing).

Containers and virtual machines. Docker Desktop runs containers in a Linux VM; on macOS, a container's connection is opened by Docker's backend (com.docker.backend), so the program inside (curl, pip…) can't be seen. Connections of these VM gateways (SignatureBuilder.vmGateways: Docker's backend and vpnkit, Podman's gvproxy, OrbStack's helper, limactl, QEMU) are judged per destination (pattern TCP pypi.org:443, not TCP internet:443) and never pass on the gateway's trusted signature: each new domain a container reaches is asked about once ("A Docker container wants to connect to pypi.org"), and Block stops it for every container. VMs with bridged or shared (NAT) networking send packets from the VM's own interface, not from a Mac process, so the relay never sees them.

In a firewall question, Ask Claude has the shortcut ⌘K.

#Hold suspicious processes (opt-in)

Settings ▸ Detection ▸ Hold suspicious processes, also in the menu bar icon (off by default). When an event adds a strong story stage, Hostwatch sends its process SIGSTOP and shows a floating panel with Allow, Always Allow (marks the pattern Safe), Kill and Ask AI. The stages are a piped or encoded command, a credential read, a login item, quarantine removal, running a just-dropped file, or a swapped binary. A program that is a new high-risk pattern is held too.

  • Only yours. The app runs as you, so root and other users' processes can't be held. Patterns marked Safe, Hostwatch itself, launchd, system UI (/System/Library/CoreServices, /System/Applications) and terminals or editors are never held. At most 5 holds at once. The pid's path is checked before every signal, so an exited, reused pid is left alone.
  • No answer in 60 s: let it continue (default) or kill it (If No Answer in 60 s).
  • Fails open. Each hold starts a detached watchdog (sleep 65; kill -CONT pid), so a process can't stay frozen if Hostwatch quits or crashes. Quitting or turning the hold off resumes everything.
  • Best effort. Events arrive after the fact, so a quick curl can finish before it is stopped. Slower steps (installers, scripts, long downloads) are caught. Blocking before execution would need Endpoint Security AUTH events or a Network Extension filter.

#Watch Closely

Right-click an event (or Activity ▸ Watch Selected Process Closely…, ⌥⌘W) to record what its process, and every process it starts, does for 30 s to 5 min (1 min by default). The collector runs a second eslogger with about 60 Endpoint Security event types (BehaviorRecorder.events, those this macOS knows): file create, write, rename, delete, permissions and quarantine changes; code loaded and memory made executable; signals, task ports, debugging and thread injection into other processes; setuid, sudo, authorization; XPC and Unix-socket connections; login items, configuration profiles, privacy (TCC) changes; kernel extensions, drivers, mounts and more. Lines are checked for the tree's pids before they're parsed, so other processes cost almost nothing. The collector's own connection sources add the network. The result is a behaviour profile (BehaviorProfile, never the raw events), sent to the app every 2 s; recording ends at the time limit, on Stop, when every watched process has exited, or when the app goes away.

The window shows What stands out first (local rules: persistence, privacy changes, injection into or control of other processes, privilege changes, keychains, SSH and cloud keys, browser data, launch agents, removed quarantine, executables made in temporary folders, mass renames), then processes as a tree, network, other processes, persistence, privileges, system, services, files grouped by folder (changes first) and event counts. When recording ends, Ask explains it with Claude or Apple's on-device model (the engine switch, as in Ask AI); the evidence is the profile, most telling first, with the signer and parent chain, editable before sending, secrets masked. Test it as root: sudo Hostwatch --watch-test <pid> [seconds] prints the highlights and the evidence.

The window's duration menu offers 30 seconds, 1, 2 or 5 minutes; Watch Again records once more.

#MCP server

A read-only Model Context Protocol server over stdio (JSON-RPC, protocol versions 2025-06-18, 2025-03-26, 2024-11-05) for Claude Code. There's no network listener: Claude Code starts the process and talks over stdin/stdout.

  • Access (Settings ▸ AI ▸ Use with Claude Code, or Help ▸ Use with Claude Code…) is off by default. Turning it on creates a random token (hwmcp_ + 64 hex) and shows the command to run once: claude mcp add --scope user hostwatch -e HOSTWATCH_MCP_TOKEN=<token> -- <path to Hostwatch.app>/Contents/MacOS/Hostwatch --mcp (it first removes an older hostwatch registration). The token is shown once: Hostwatch keeps only its SHA-256 in mcp-token.sha256 (mode 600) and compares in constant time.
  • Refusals: with access off, or a missing or outdated token, the server answers every request with an error (-32001) saying how to fix it, and serves no data. New Token… invalidates earlier registrations; turning access off invalidates all of them.
  • Access log: each session start is recorded (time, allowed/refused, the program that started it) in mcp-access.log; the last five show in Settings.
  • Limits of a token: it keeps out MCP clients you didn't set up, and makes access revocable and visible. A program already running as your user could still read Hostwatch's files directly, as it can any of your files.

#Exclusions

One pattern per line, case-insensitive, # for comments. A pattern with * or ? is a glob that must match the whole value; anything else is a substring match.

mdworker              # hide everything from matching processes (name or path)
proc:/usr/libexec/*   # hide spawns of matching executables
net:*:53              # hide connections to matching remote host:port
net:17.*              # hide connections to Apple's 17.0.0.0/8 range
file:/System/*        # hide opens of matching file paths
file:*.plist

Sensible noise defaults (/System, /usr/lib, caches, loopback, Spotlight) are preloaded; Restore Defaults in the editor brings them back. Exclusions persist in UserDefaults (local.hostwatch.app).

#Activity history

All activity is written to disk as JSON Lines, one event per line, with a full ts timestamp:

~/Library/Logs/Hostwatch/History/activity-20261031-202536-385.jsonl
{"kind":"net","time":"20:25:36","pid":812,"ppid":1,"name":"curl","proc":"/usr/bin/curl","target":"140.82.112.3:443","extra":"TCP","ts":"2026-10-31T20:25:36.385+02:00"}
  • Compression: the file being written stays plain, so appends are cheap and a crash loses nothing. When it is full (see Max size below), it is compressed in the background (≈1 s per 100 MB) into activity-….jsonl.gz plus a small index activity-….jsonl.idx. Plain files left from older versions are compressed on the next start. Activity logs are very repetitive: on real history, 250 MB became ≈10 MB (≈24×).
    • The .gz is a series of independent gzip members of ≈4 MB of whole lines, so it is a normal gzip file (zcat, zgrep, gzip -d work).
    • The index records each block's earliest and latest timestamp, offset and sizes, plus bytes per minute. Time Travel and the MCP server decompress only the blocks a time range needs, and the timeline's bars come from the per-minute counts (exact, with real gaps).
    • Compression is crash-safe: the index is written first, then the .gz, and only then is the plain file removed. A .gz without an index is ignored, and the plain file stays authoritative.
  • Max size (default 5 GB) caps the bytes on disk of all history files (compressed files count compressed, so the cap holds roughly 10–20× more history than before). Files rotate at about 1/20 of the cap (1–100 MB of plain text each; 100 MB with the default cap). The cap covers everything recorded in the folder together: activity (activity-*), resource samples (metrics-*) and process lists (processes-*); there is no separate limit for any of them. When the total would go over, the oldest day goes first (its activity, then its samples and process lists), checked when a file rotates and every 10 minutes. Today's files and the file being written are never deleted.
  • The recorder has its own connection with the 40/s display cap turned off. It keeps recording while the overlay is paused or a kind is hidden.
  • Apply exclusions to history is off by default, so everything is recorded. Turn it on to record only what passes your exclusions.
  • Settings ▸ History: on/off, maximum size (500 MB … 50 GB or Custom…), location, Show in Finder, Clear History…. The activity window footer shows current usage.
  • Query examples: ``bash cd ~/Library/Logs/Hostwatch/History zcat -f activity-*.jsonl* 2>/dev/null | jq -c 'select(.kind=="net")' | tail zgrep -h '"name":"curl"' activity-*.jsonl.gz; grep -h '"name":"curl"' activity-*.jsonl ``
  • Tools: --story-replay and --signature-report accept a .jsonl, a .jsonl.gz or the whole history folder; --compress-history <folder> compresses plain files by hand; --time-travel-probe prints read timings.

#How the collector works

The collector is built into the app (Hostwatch --collector, Swift; until 0.5 it was a Python script). The launcher starts it as root, and it combines:

  • eslogger exec exit open (Endpoint Security) → processes and file opens (exit is only used to keep the list of Hostwatch's own processes exact; it is never published). Opens are deduplicated per (pid, path) for 2 minutes and capped at 40/s per client.
  • Packet capture (tcpdump -i pktap,all -k NPD -Z nobody, read-only; it drops root right after opening the capture device, so packets are decoded without root) → every outgoing TCP connection, from its SYN packet, with the owning process. This catches connections too short for any polling, like curl google.com. Endpoint Security has no connect event.
  • Every process's connected sockets, read with libproc every second and compared with the previous look → incoming connections, long-lived UDP flows, and a fallback if packet metadata is unavailable. Each connection is reported once, by whichever source sees it first. (Before 0.9 this was lsof -i.)
  • macOS's connection statistics (NetworkStatistics.framework, what nettop is built on) → every new TCP and UDP socket of every process, with its real destination, even one that closes within milliseconds. This matters with security tools that take over TCP flows in the kernel (e.g. a traffic-scanning network extension): their short connections never appear as packets from the process. The framework is private, so it's opened at run time; if a macOS ever lacks it, the collector falls back to running nettop (under a small shell that stops it if the collector dies) and reports a new process with TCP traffic nobody else reported as an inferred connection, its destination taken from what nettop saw or the command line (≈name), marked as inferred with byte counts.
  • Passive DNS answers (tcpdump, port 53, read-only) → a hostname for each new connection: the name that resolved to its IP, e.g. curl TCP www.google.com:80, kept even behind CNAMEs. If no answer was seen (cached before the collector started, or encrypted DNS/DoH), reverse DNS is used instead, shown as ~name (often a provider name like ~bt-in-f100.1e100.net). The Activity list still shows the IP, Claude gets both, and exclusions match hostnames: net:*.google.com:*.

Hostwatch's own activity is not reported (live, in history or in stories): the app that started the collector (verified by pid), the collector's own helpers (eslogger, tcpdump, nettop if used) and the children of these. Other runs of the Hostwatch program, such as the MCP server Claude Code starts, are reported like any program: hiding "anything running the Hostwatch binary" would let malware hide by starting it with injected code. A pid leaves the list when its process exits, so a reused pid is watched again.

Options: ./scripts/run-agent.sh --no-files --no-net --net-interval 0.5 --socket /var/run/hostwatch/collector.sock. Started by hand, the collector accepts connections only from the user who ran sudo. For development, HOSTWATCH_SOCKET points the app at another socket path (then its folder need not be root-owned).

The HUD sends its exclusions and enabled kinds to the agent, which filters per client before sending, so exclusions also reduce load.

#Security notes

  • Hardened runtime. The app is signed with --options runtime (ad-hoc builds too; build-app.sh refuses to finish without it). macOS then ignores DYLD_INSERT_LIBRARIES and similar variables and loads only Apple-signed libraries into Hostwatch, so code can't be injected into the app, the root collector or the MCP server (verified: a test library injected into a build without the flag ran, with the flag it doesn't).
  • Collector channel. The collector serves a Unix socket, /var/run/hostwatch/collector.sock, never a network port:
    • The folder is created by root with mode 0755, and the collector refuses a folder it doesn't own, so no other process can create or replace the socket. A leftover socket is replaced; any other file is not.
    • The socket belongs to the client user with mode 0600 (other users cannot connect).
    • Every connection is checked with the kernel's peer credentials (LOCAL_PEERPID, LOCAL_PEERCRED): when launched by the app, only that app process (and user) is accepted; started by hand, only the sudo user. Rejections are logged with the process path.
    • The app connects only when the socket is a socket owned by you, mode 0600, in a root-owned folder that nobody else can write (and not a link). Otherwise it refuses and the HUD says why, so a fake collector run by an ordinary user cannot feed it data.
  • New-process events carry the command line, which is forwarded to the app, shown, given to Claude and written to history. Secrets are masked first (Secrets, one rule set): Authorization and API-key headers and cookies, name=value / --name value for password, token, secret, API/access/ private key, auth, session and signature (GITHUB_TOKEN=, ?token=, --password too), URL credentials (user:pass@, token@), curl -u, security … -w, sshpass -p, mysql -p…, known token formats (ghp_, github_pat_, glpat-, xox…, sk-, AKIA/ASIA, AIza, npm_, hf_), JWTs and private key blocks. History shows ***; AI prompts [REDACTED].
  • Nothing unmasked goes to an AI: every prompt (Ask AI, pattern suggestions, rule proposals, domain details, on-device or Claude) is masked again right before it's sent, whatever built it. MCP output too.
  • Older history is masked too: once, in the background, finished history files are re-masked (compressed ones rewritten with a new index), and every file is masked again before it's compressed. A secret in a shape no rule knows can still slip through. Environment variables are never forwarded.
  • To find connections, the collector runs tcpdump (DNS answers and TCP SYN headers only, no payloads) as root and reads macOS's connection statistics, read-only. Nothing is captured to disk.
  • eslogger is a notify-only observer. It cannot deny execution.
  • Config lines sent by clients are only used as filters; the agent runs no commands based on them.
  • The HUD itself runs as the logged-in user; only the collector is elevated.
  • The collector is the app's own binary, run as root (--collector-launcher … --collector). Keep the app somewhere only you can write to (e.g. /Applications), or anything that can modify it gains root on next start.
  • The shutdown command additionally needs the per-launch token from collector.token (mode 0600).

#Troubleshooting

  • Nothing appears / "Collector off": start it from the menu bar icon; check Help ▸ Collector Log.
  • ERR_NOT_PERMITTED in the log: Full Disk Access is missing (see Built-in collector). Ad-hoc builds need the grant redone after every rebuild.

#Known limitations

  • The firewall can't tell containers apart or name the program inside one: a container's connections are Docker's (or Podman's, OrbStack's…), judged per destination. VMs with bridged or NAT networking aren't covered at all.
  • Very short connections are caught by packet capture and by macOS's connection statistics. Only with the nettop fallback (a macOS without that framework) do they arrive ~2 s late with a destination inferred from the command line. UDP sent without connecting (sendto) has no destination to show, and listening sockets aren't connections.
  • File opens are high volume. The rate cap drops excess file events, so add exclusions for noisy apps.
  • The eslogger JSON parser is defensive but may need updates across macOS releases.

#Prototype notes

Apple documents eslogger as a tool for exploring and prototyping, not an application API: its JSON may change without notice. For a distributable tool, replace the collector with a native Endpoint Security system extension (com.apple.developer.endpoint-security.client entitlement) and a Network Extension for connections.

#Production architecture

For production, implement a signed Endpoint Security system extension and use XPC or a protected local IPC channel to communicate with this HUD. The system extension should subscribe only to the event types required, process callbacks quickly, and avoid blocking ES callbacks on UI or disk I/O. Apple's ES entitlement must be approved for the developer team. Do not disable SIP as a routine installation workaround.
